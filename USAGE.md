## Общий вид интерфейса

Слева — панель со списком проектов и кнопкой «+» для создания нового.
Каждый проект соответствует одному будущему ZIP-архиву (`benchmark-xccdf.xml`
+ один или несколько `checks-*.xml`). Справа — рабочая область с вкладками
конкретного открытого проекта:

- **Бенчмарк** — общие метаданные (id, язык, статус, название, описание, версия).
- **Профили** — наборы правил, которые войдут в конкретный вариант проверки.
- **Правила** — отдельные проверки со ссылкой на техническую логику в OVAL.
- **OVAL-файлы** — техническая часть: definitions/tests/objects/states/variables.
- **Валидация и экспорт** — проверка на соответствие требованиям и скачивание ZIP.

## Режим «Мастер» и режим «Конструктор»

Над вкладками открытого проекта есть переключатель **мастер / конструктор**.

- **Мастер** — рекомендуемый режим для последовательного заполнения профиля
  «с нуля»: пять пронумерованных шагов (бенчмарк → профили → правила →
  OVAL-файлы → валидация и экспорт) с кнопками «назад/далее», подсказкой на
  каждом шаге и всплывающим окном-пояснением при первом посещении шага
  (можно один раз отметить «больше не показывать»). После сохранения
  профиля/правила/OVAL-файла/definition/test/object/state/variable сервис
  сам спрашивает, не нужно ли сразу добавить ещё один такой же элемент —
  это удобно, когда в разделе много однотипных параметров.
- **Конструктор** — прежний свободный доступ ко всем вкладкам в любом
  порядке, без пошагового сценария. Оба режима работают с одним и тем же
  проектом и одними и теми же данными: можно в любой момент переключиться
  между ними, в том числе при редактировании уже сохранённого проекта —
  ничего не теряется и не блокируется.

Значок «?» рядом со сложными полями (например, `criteria`, `check`,
`object_ref`) открывает короткую всплывающую подсказку по этому полю.

## Тёмная и светлая тема

Кнопка-переключатель находится в верхней части боковой панели, рядом с
названием сервиса (значок ☾ / ☀). Выбор темы запоминается в браузере и
применяется автоматически при следующем открытии страницы.

## Создание проекта

1. Нажмите **«+»** рядом с заголовком «Проекты».
2. Заполните форму:
   - **Идентификатор проекта** — техническое имя папки на сервере (латиница,
     цифры, `-`, `_`). Не показывается в самом бенчмарке, служит только для
     хранения на диске.
   - **Benchmark/@id** — идентификатор бенчмарка в самом XCCDF-файле,
     например `xccdf_custom_benchmark_windows`.
   - **xml:lang** — язык содержимого (по умолчанию `ru-RU`).
   - **status** — статус бенчмарка (`draft`/`accepted`/... с русской подписью).
   - **title**, **description**, **version** — название, описание и версия
     бенчмарка.
3. Нажмите «Создать проект» — откроется рабочая область нового проекта.

## Вкладка «Бенчмарк»

Здесь можно в любой момент отредактировать статус, название, описание и
версию бенчмарка (идентификатор и язык фиксируются при создании и не
меняются). Изменения сохраняются кнопкой «Сохранить».

## Вкладка «OVAL-файлы»

Один проект может содержать несколько OVAL-файлов (в требованиях допускается
несколько `checks-*.xml` в одном архиве).

1. **«+ OVAL-файл»** — создать новый файл, указав его имя (например,
   `checks-oval.xml`) и метаданные генератора (product_name, product_version,
   schema_version).
2. Выберите файл из списка чипов — откроется его содержимое с подвкладками:
   - **Variables** — константные переменные (`constant_variable`), которые
     затем можно подставлять в States вместо конкретного значения.
   - **Objects** — объекты проверки. При создании выбирается **тип теста**
     (все 18 допустимых типов из требований, с русским названием и
     техническим идентификатором через тире, например «Политика паролей —
     windows:passwordpolicy_test»); форма полей подстраивается под выбранный
     тип автоматически.
   - **States** — ожидаемые состояния/значения для сравнения. Для полей,
     которые это допускают, можно либо ввести значение и оператор сравнения
     напрямую, либо переключиться на «переменная» и сослаться на созданную
     ранее Variable.
   - **Tests** — связывает Object (и, если нужно, State) с конкретным типом
     проверки; здесь же задаются атрибуты `check` и `check_existence`.
   - **Definitions** — итоговая проверка (`definition`) с метаданными
     (название, описание, платформа) и списком критериев (`criteria`),
     каждый из которых ссылается на Test.

     Поля `family` и `platforms` у definition — не одно и то же:
     - **family** — фиксированное перечисление самого стандарта OVAL
       (`windows`/`unix`/`linux`/`independent`), менять его на конкретные
       дистрибутивы нельзя — это сломает валидность OVAL-файла;
     - **platforms** — свободный текст (список через запятую), сюда как раз
       вписываются конкретные системы, для которых актуален definition. Под
       полем есть кнопки быстрой вставки целевых ОС проекта (РЕД ОС, ALT
       Linux, Astra Linux, Debian, Ubuntu, Windows) — можно нажать
       нужные вместо того, чтобы печатать вручную.

**Рекомендуемый порядок заполнения одного OVAL-файла:** Variables (если
нужны) → Objects → States → Tests → Definitions — именно в таком порядке
каждая следующая сущность ссылается на уже существующие предыдущие.

## Вкладка «Правила»

Правило (`Rule`) — то, что в итоге увидит пользователь профиля. Каждое
правило ссылается на конкретный `definition` внутри одного из OVAL-файлов
проекта (поля «check-content-ref/@href» и «check-content-ref/@name»).

1. **«+ Правило»** доступно только после того, как в проекте есть хотя бы
   один OVAL-файл.
2. Заполните id, признак «выбрано по умолчанию» (`selected`), название,
   описание, при необходимости — один или несколько `ident` (система
   идентификаторов требований + значение).
3. В полях «check-content-ref» укажите OVAL-файл и id нужного `definition`.

## Вкладка «Профили»

Профиль (`Profile`) — именованный набор правил (например, «базовый» и
«усиленный» уровень защищённости на основе одного и того же набора правил).

1. **«+ Профиль»** — id, название, описание, необязательная ссылка на
   документ-основание (`reference`).
2. Кнопка **«Правила профиля»** у каждого профиля открывает список всех
   правил проекта с чекбоксами — отметьте, какие правила входят в профиль.
   Внутри это генерирует элементы `select` с `idref` на правило и атрибутом
   `selected="true"`.

## Вкладка «Валидация и экспорт»

- **«Проверить проект»** — прогоняет полный набор проверок из требований:
  обязательные поля, уникальность и формат идентификаторов
  (`oval:<namespace>:<type>:<number>`), связность всех ссылок
  (`select → Rule`, `check-content-ref → definition`, `criterion → test`,
  `test → object/state` с проверкой совпадения типов, `var_ref → variable`).
  Ошибки (`error`) блокируют корректный импорт архива, замечания (`warning`)
  — это рекомендации, не блокирующие работу.
- **«Экспортировать ZIP»** — скачивает архив `<project_id>.zip` в формате
  `benchmark-xccdf.xml` + `checks-*.xml` в корне, готовый к импорту.

## Импорт готового архива

Кнопка «Импорт ZIP…» в нижней части боковой панели позволяет загрузить уже
готовый архив (например, для доработки существующего профиля) — сервис
проверит, что в архиве ровно один XCCDF-файл, хотя бы один OVAL-файл и все
файлы лежат в корне архива (без вложенных папок), после чего создаст из него
новый проект с указанным вами идентификатором.

## Типичные ошибки валидации и как их исправить

| Сообщение | Причина | Как исправить |
|---|---|---|
| «не заполнено обязательное поле…» | Пустое title/description/status/version | Заполнить поле на соответствующей вкладке |
| «ссылается на несуществующее правило» | В профиле выбрано правило, которого больше нет | Снять выбор в «Правила профиля» или создать правило заново |
| «не задана ссылка check-content-ref» | Не указаны href/name у правила | Указать OVAL-файл и id definition в правиле |
| «идентификатор не соответствует формату» | id не вида `oval:<namespace>:<type>:<number>` | Исправить id сущности |
| «идентификатор не уникален в рамках комплекта файлов» | Один и тот же id использован дважды (в т.ч. в разных файлах) | Переименовать один из дублирующихся id |
| «object_ref/state_ref не найден» | Test ссылается на удалённый Object/State | Пересоздать ссылку в Test |
| «object несовместимого типа» | Test и Object/State созданы для разных типов проверки | Использовать Object/State того же типа, что и Test |
| «var_ref не найден среди variables» | State ссылается на несуществующую переменную | Создать переменную или изменить ссылку |
